# 部署运维计划

## 1. 基础设施架构 (AWS + Kubernetes)

### 1.1 AWS 资源配置

#### 核心服务
- **EKS (Elastic Kubernetes Service)**: 托管 Kubernetes 集群
  - 版本: 1.28+
  - 节点组: 3 个可用区分布
  - 自动扩缩容: 3-10 节点
- **RDS (PostgreSQL)**: 主数据库
  - 实例类型: db.r6g.xlarge (生产环境)
  - Multi-AZ 部署
  - 自动备份: 每日 + 7 天保留
- **ElastiCache (Redis)**: 缓存层
  - 实例类型: cache.r6g.large
  - 集群模式: 启用
  - 副本数: 2
- **S3**: 对象存储
  - 红包图片/附件存储
  - 日志归档
  - 备份存储
- **CloudFront**: CDN 加速
  - 静态资源分发
  - 全球边缘节点
- **Route 53**: DNS 管理
  - 健康检查
  - 故障转移路由

#### 网络架构
```
VPC (10.0.0.0/16)
├── Public Subnets (3 AZs)
│   ├── NAT Gateway
│   └── Application Load Balancer
├── Private Subnets (3 AZs)
│   ├── EKS Worker Nodes
│   └── Application Pods
└── Database Subnets (3 AZs)
    ├── RDS Primary/Standby
    └── ElastiCache Cluster
```

#### 安全配置
- **IAM Roles**: 最小权限原则
  - EKS Node Role
  - Pod Service Accounts (IRSA)
  - CI/CD Deploy Role
- **Security Groups**: 严格入站规则
  - ALB: 仅 443/80
  - EKS Nodes: 仅集群内通信
  - RDS: 仅 EKS 安全组
- **Secrets Manager**: 敏感信息管理
  - 数据库密码
  - API Keys
  - 证书私钥

## 2. CI/CD 流程 (GitHub Actions)

### 2.1 工作流配置

#### 主流程文件: `.github/workflows/deploy.yml`
```yaml
name: Deploy to Production

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  AWS_REGION: ap-southeast-1
  ECR_REPOSITORY: spring-festival-ops
  EKS_CLUSTER: spring-festival-prod

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run linting
        run: npm run lint

      - name: Run tests
        run: npm run test:ci

      - name: Upload coverage to Codecov
        uses: codecov/codecov-action@v3
        with:
          files: ./coverage/lcov.info

  build:
    needs: test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Docker meta
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ steps.login-ecr.outputs.registry }}/${{ env.ECR_REPOSITORY }}
          tags: |
            type=sha,prefix={{branch}}-
            type=raw,value=latest

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          build-args: |
            BUILD_DATE=${{ github.event.head_commit.timestamp }}
            VCS_REF=${{ github.sha }}

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Update kubeconfig
        run: |
          aws eks update-kubeconfig --name ${{ env.EKS_CLUSTER }} --region ${{ env.AWS_REGION }}

      - name: Deploy to Kubernetes
        run: |
          kubectl set image deployment/spring-festival-api \
            api=${{ needs.build.outputs.image-tag }} \
            -n production

          kubectl rollout status deployment/spring-festival-api -n production --timeout=5m

      - name: Notify Sentry of deployment
        uses: getsentry/action-release@v1
        env:
          SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
          SENTRY_ORG: ${{ secrets.SENTRY_ORG }}
          SENTRY_PROJECT: spring-festival-ops
        with:
          environment: production
          version: ${{ github.sha }}

  rollback:
    needs: deploy
    runs-on: ubuntu-latest
    if: failure()

    steps:
      - name: Rollback deployment
        run: |
          kubectl rollout undo deployment/spring-festival-api -n production
          kubectl rollout status deployment/spring-festival-api -n production
```

## 3. 监控告警体系

### 3.1 Sentry (错误追踪)

#### 集成配置
```typescript
// src/lib/sentry.ts
import * as Sentry from '@sentry/node';

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  environment: process.env.NODE_ENV,
  release: process.env.GIT_SHA,

  // 性能监控
  tracesSampleRate: 0.1,

  // 错误过滤
  beforeSend(event, hint) {
    // 过滤敏感信息
    if (event.request) {
      delete event.request.cookies;
      delete event.request.headers?.authorization;
    }
    return event;
  },

  // 集成
  integrations: [
    new Sentry.Integrations.Http({ tracing: true }),
    new Sentry.Integrations.Express({ app }),
  ],
});
```

#### 告警规则
- **Critical**: 5xx 错误率 > 1% (5分钟内)
- **High**: 数据库连接失败
- **Medium**: API 响应时间 > 2s (P95)
- **Low**: 弃用 API 调用

#### 通知渠道
- Slack: `#alerts-production`
- PagerDuty: 紧急事件 (Critical)
- Email: 开发团队

## 4. 备份与恢复策略

### 4.1 数据库备份

#### 自动备份 (RDS)
- **频率**: 每日 03:00 UTC
- **保留期**: 7 天
- **备份窗口**: 03:00-04:00 UTC
- **快照**: 每周日完整快照 (保留 4 周)

#### 手动备份脚本
```bash
#!/bin/bash
# backup-database.sh

TIMESTAMP=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="db_backup_${TIMESTAMP}.sql.gz"
S3_BUCKET="s3://spring-festival-backups/database"

# 导出数据库
pg_dump -h $DB_HOST -U $DB_USER -d $DB_NAME | gzip > $BACKUP_FILE

# 上传到 S3
aws s3 cp $BACKUP_FILE $S3_BUCKET/$BACKUP_FILE

# 验证备份
aws s3 ls $S3_BUCKET/$BACKUP_FILE

# 清理本地文件
rm $BACKUP_FILE

echo "Backup completed: $BACKUP_FILE"
```

### 4.2 应用状态备份

#### Kubernetes 资源备份 (Velero)
```bash
# 安装 Velero
velero install \
  --provider aws \
  --plugins velero/velero-plugin-for-aws:v1.8.0 \
  --bucket spring-festival-k8s-backups \
  --backup-location-config region=ap-southeast-1 \
  --snapshot-location-config region=ap-southeast-1

# 创建定时备份
velero schedule create daily-backup \
  --schedule="0 2 * * *" \
  --include-namespaces production \
  --ttl 168h
```

### 4.3 恢复流程

#### 数据库恢复
```bash
# 1. 下载备份文件
aws s3 cp s3://spring-festival-backups/database/db_backup_20260216_030000.sql.gz .

# 2. 解压
gunzip db_backup_20260216_030000.sql.gz

# 3. 恢复到数据库
psql -h $DB_HOST -U $DB_USER -d $DB_NAME < db_backup_20260216_030000.sql

# 4. 验证数据完整性
psql -h $DB_HOST -U $DB_USER -d $DB_NAME -c "SELECT COUNT(*) FROM red_packets;"
```

#### Kubernetes 资源恢复
```bash
# 查看可用备份
velero backup get

# 恢复指定备份
velero restore create --from-backup daily-backup-20260216

# 查看恢复状态
velero restore describe daily-backup-20260216
```

#### 灾难恢复 (DR) 演练
**频率**: 每季度一次

**步骤**:
1. 在 Staging 环境模拟故障
2. 从备份恢复数据库
3. 重新部署应用
4. 验证功能完整性
5. 记录恢复时间 (RTO)
6. 评估数据丢失 (RPO)

**目标**:
- RTO (恢复时间目标): < 1 小时
- RPO (恢复点目标): < 15 分钟

## 5. SLA 保障 (99.9% 可用性)

### 5.1 可用性计算

**目标**: 99.9% 年度可用性
- 允许停机时间: 8.76 小时/年 (43.8 分钟/月)
- 实际目标: 99.95% (留有缓冲)

### 5.2 高可用架构

#### 多层冗余
```
Layer 1: DNS (Route 53)
  ├── Health Check
  └── Failover Routing

Layer 2: Load Balancer (ALB)
  ├── Multi-AZ
  └── Auto Scaling

Layer 3: Application (EKS)
  ├── 3+ Replicas
  ├── Pod Anti-Affinity
  └── HPA

Layer 4: Database (RDS)
  ├── Multi-AZ
  ├── Read Replicas (2)
  └── Automated Failover

Layer 5: Cache (ElastiCache)
  ├── Cluster Mode
  └── 2 Replicas
```

#### 故障转移策略
- **应用层**: 滚动更新 (零停机)
- **数据库层**: 自动故障转移 (< 60s)
- **缓存层**: 客户端自动重连
- **跨区域**: 主动-被动 DR (手动切换)

### 5.3 性能优化

#### 响应时间目标
- API 响应时间 (P95): < 200ms
- API 响应时间 (P99): < 500ms
- 数据库查询 (P95): < 50ms
- 缓存命中率: > 90%

#### 优化措施
1. **数据库优化**
   - 索引优化
   - 查询优化 (EXPLAIN ANALYZE)
   - 连接池配置 (max: 20)

2. **缓存策略**
   - Redis 缓存热点数据
   - CDN 缓存静态资源
   - 应用层缓存 (内存)

3. **代码优化**
   - 异步处理 (消息队列)
   - 批量操作
   - 懒加载

### 5.4 容量规划

#### 流量预估 (春节高峰)
- 峰值 QPS: 10,000
- 日活用户: 500,000
- 并发连接: 50,000

### 6.2 常见问题处理

#### Pod 无法启动
```bash
# 1. 查看 Pod 状态
kubectl get pods -n production

# 2. 查看详细信息
kubectl describe pod <pod-name> -n production

# 3. 查看日志
kubectl logs <pod-name> -n production --previous

# 4. 常见原因
# - 镜像拉取失败: 检查 ECR 权限
# - 资源不足: 检查节点资源
# - 配置错误: 检查 ConfigMap/Secret
```

#### 数据库连接池耗尽
```bash
# 1. 检查当前连接数
psql -h $DB_HOST -U $DB_USER -c "SELECT count(*) FROM pg_stat_activity;"

# 2. 查看活跃查询
psql -h $DB_HOST -U $DB_USER -c "SELECT pid, query, state FROM pg_stat_activity WHERE state = 'active';"

# 3. 终止长时间运行的查询
psql -h $DB_HOST -U $DB_USER -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'active' AND query_start < NOW() - INTERVAL '5 minutes';"

# 4. 调整连接池配置
# 编辑应用配置: DATABASE_POOL_MAX=30
```

#### 缓存失效导致数据库压力
```bash
# 1. 检查 Redis 状态
redis-cli -h $REDIS_HOST INFO stats

# 2. 检查缓存命中率
redis-cli -h $REDIS_HOST INFO stats | grep keyspace_hits

# 3. 预热缓存
node scripts/warm-cache.js

# 4. 临时扩容数据库读副本
aws rds create-db-instance-read-replica --db-instance-identifier prod-read-replica-temp
```

### 6.3 紧急回滚流程

```bash
# 1. 立即回滚到上一个版本
kubectl rollout undo deployment/spring-festival-api -n production

# 2. 验证回滚状态
kubectl rollout status deployment/spring-festival-api -n production

# 3. 检查应用健康
kubectl get pods -n production -l app=spring-festival-api

# 4. 通知团队
curl -X POST $SLACK_WEBHOOK_URL \
  -H 'Content-Type: application/json' \
  -d '{"text":"🚨 Production rollback completed. Version: previous"}'

# 5. 创建事故报告
# - 记录回滚时间
```

## 7. 安全与合规

### 7.1 安全措施
- **网络隔离**: VPC + Security Groups
- **加密**:
  - 传输层: TLS 1.3
  - 存储层: RDS/S3 加密
- **身份认证**:
  - IAM Roles (AWS)
  - RBAC (Kubernetes)
  - JWT (应用层)
- **漏洞扫描**:
  - Trivy (容器镜像)
  - Snyk (依赖包)
- **审计日志**: CloudTrail + Kubernetes Audit

### 7.2 合规要求
- **数据保护**: GDPR/个人信息保护法
- **日志保留**: 90 天
- **访问控制**: 最小权限原则
- **变更管理**: 所有变更需审批

## 8. 成本优化

### 8.1 优化策略
- **Spot Instances**: 非关键工作负载使用 Spot 实例 (节省 70%)
- **Reserved Instances**: RDS/ElastiCache 使用预留实例 (节省 40%)
- **Auto Scaling**: 根据流量自动调整资源
- **S3 生命周期**: 旧日志/备份自动归档到 Glacier
